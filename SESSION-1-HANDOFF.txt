4. KEY GOTCHAS DISCOVERED (do not re-debug these)
--------------------------------------------------------------------------------

GOTCHA 1 - AI: max_output_tokens includes REASONING tokens
  Model is gpt-5-nano (a reasoning model). With effort "low" and a 180 cap, all
  128 output tokens were consumed by reasoning and ZERO text was produced ->
  route threw -> 502 "The drafting assistant is temporarily unavailable."
  Measured:  low/180 = fail, minimal/300 = works (0 reasoning tokens).
  FIXED: all 3 routes now use reasoning:{effort:"minimal"} and higher caps.
  OPENAI_PORTAL_MAX_OUTPUT_TOKENS must be 400, NOT 180. .env still says 180;
  .env.local and Vercel say 400.
  All three AI routes were broken, not just the visible one:
    /api/portal/admin/ai-assist   (attorney draft reply / summarize)
    /api/portal/recommendations   (silently fell back to rule text)
    /api/portal/ai-suggestions    (cap was hardcoded 100 - never worked)

GOTCHA 2 - SMTP is slow (~10s per email)
  Measured GoDaddy smtpout.secureserver.net: connect+auth ~4s, sendMail ~6s.
  Provisioning sends 2 emails; they were sequential (~20s+) which exceeded the
  serverless limit. Now concurrent + maxDuration=60.

GOTCHA 3 - Local ISP blocks outbound port 587
  Ports tested from the dev machine: 587 BLOCKED, 465 OPEN, 25 BLOCKED.
  .env.local overrides SMTP_PORT=465 / SMTP_SECURE=true for local dev only.
  PRODUCTION MUST STAY ON 587 (Vercel is not blocked).

GOTCHA 4 - Never run `npm run build` while `next dev` is running
  Both write to .next. Doing so corrupted the route tree and produced a
  site-wide 404 (twice). Correct order: Ctrl+C the dev server, then
  Remove-Item -Recurse -Force .next, then npm run dev.

GOTCHA 5 - .env uses "KEY = value" with SPACES around =
  A grep for '^KEY=' misses them. dotenv trims whitespace so they load fine.
  An early audit wrongly reported MAILER_*/SMTP_*/SUPPORT_* as missing.

GOTCHA 6 - Firebase Admin private key formatting
  In a .env file: ONE line, double-quoted, literal \n.
  In Vercel: real line breaks, NO quotes, and the -----BEGIN/-----END PEM armor
  lines MUST be included (the user initially pasted only the base64 body, which
  crashed every portal page).

GOTCHA 7 - Preview mode
  Many portal pages accept ?preview=1 (dev only) and fake an admin session.
  If the dashboard renders but a sub-page redirects to login, check for
  ?preview=1 in the URL.

5. ACTIVE BUG BEING FIXED RIGHT NOW (uncommitted)
--------------------------------------------------------------------------------
SYMPTOM: Attorney clicks "Create client and send invitation".
         The client account IS created and the correct setup email IS delivered,
         but the UI shows red: "The invitation service is unavailable. Please
         try again."

ROOT CAUSE: React nulls out event.currentTarget once an async handler yields.
  PortalInviteForm.submit() did:
      if (response.ok) { event.currentTarget.reset(); ... }
  ...AFTER `await fetch` and `await response.json()`. So on SUCCESS it threw
  TypeError (reading 'reset' of null), which the surrounding catch swallowed and
  replaced with the generic network-failure message.
  It only misfires on success, which is exactly why the email arrives.

  NOTE: an earlier theory in this session blamed a serverless timeout. That was
  WRONG for this symptom (the SMTP slowness is real and worth the fix, but it is
  not what produces this error). Do not re-chase the timeout.

FIX APPLIED (uncommitted, lint passes):
  - PortalInviteForm.jsx: capture `const formElement = event.currentTarget`
    BEFORE the first await; use formElement.reset(); log the real error in catch.
  - PortalCaseWorkspace.jsx: same defect in its billing-consent submit handler,
    same fix.

Scanned the other portal forms - ExistingTrademarkRequestForm, PasswordActionForm,
PortalTeamManager, ClientPortalDashboard, PortalLoginForm are all clean.

11. ADDENDUM - NMI CUSTOMER VAULT REGRESSION (found and fixed after section 5)
--------------------------------------------------------------------------------
SYMPTOM: A real paying customer was declined at checkout.
  NMI: response 3, code 300,
       "Your account is not set up to use the Customer Vault. REFID:147090171"
  response 3 = gateway error, NOT a card decline. No transaction was created,
  so nobody was double charged - but the order was lost.

CAUSE: A REGRESSION INTRODUCED BY THE PORTAL MERGE (commit 1c6725a).
  Verified with: git log -S "customer_vault" -- app/api/nmi/charge/route.js
  Before the merge (28c4a92) the charge route sent ONLY:
    security_key, payment_token, type, amount, currency,
    first_name, last_name, email, zip, order_description
  No vault fields, and no "save my card" checkbox existed.
  The merge brought in the reference release's saved-card billing. The NMI
  merchant account does not have the Customer Vault add-on, and NMI rejects the
  ENTIRE sale rather than just skipping the vault.
  Only customers who TICKED "Save this payment method" were affected (the box
  defaults to unchecked), so it was a silent partial conversion loss.

FIX (this session):
  - New flag NEXT_PUBLIC_NMI_CUSTOMER_VAULT_ENABLED, default "false".
  - app/api/nmi/charge/route.js: vault params only sent when the flag is true;
    plus an automatic retry WITHOUT vault params if the gateway still rejects
    for a vault reason (safe - response 3 means no transaction existed).
  - components/form/NmiPayment.jsx: the save-card checkbox is hidden unless the
    flag is true, and savePaymentMethodRef is forced false regardless.
  With the flag false, checkout behaves exactly as it did pre-merge.

CONSEQUENCE: the portal "charge saved method" feature cannot work until NMI
enables Customer Vault on the account. It will simply have no saved methods,
which is correct behaviour rather than an error.

TO ENABLE SAVED CARDS LATER: have NMI provision Customer Vault, then set
NEXT_PUBLIC_NMI_CUSTOMER_VAULT_ENABLED=true in Vercel and redeploy. No code
change needed.
